# Publish a project to Andocs

1. Read `bunx andocs@latest publish --help`.
2. Find the project folder and its documentation root. New projects use `docs/` as described in [the introduction guide](introduction.md). If documents are at the project root, move the documents and their prototype assets into `docs/` before the dry run. Repository-root documentation cannot be published. Confirm the target with the user. Sign in with `bunx andocs@latest login` when needed. Use `organizations list`, `projects list`, and `projects repositories --help` to find existing target IDs.
3. Run `bunx andocs@latest publish --root <project-folder> --documents-root <docs-folder> --dry-run --json`. For an existing linked repository, also pass `--project <id> --repository <id>` to check its configured documentation path. Show the selected files and the `omitted` files with their reasons.
4. Run `bunx andocs@latest publish --root <project-folder> --documents-root <docs-folder> --json` with explicit target flags. For an existing project, add `--organization <id> --project <id> --repository <id>`. To create a private repository in an existing project, add `--organization <id> --project <id> --owner <github-login> --name <repo-name>`. This requires organization admin or owner access and asks approval only for the repository. Do not combine `--repository` with `--owner` or `--name`. For its dry run, use `--project <id> --owner <github-login> --name <repo-name>`. For a new project, add `--organization <id> --project-name <name> --owner <github-login> --name <repo-name>`. For a new personal organization, use `--organization-name <name> --project-name <name> --owner <personal-github-login> --name <repo-name>`.
5. If the result is `needs-confirmation`, ask the user each returned `question` as y/n. After each y, run that confirmation's `command` with `bunx andocs@latest` in place of `andocs`. It passes `--approve-creation <operation>:<kind>:<digest> --url <server-origin> --json`. A refusal ends the flow. Each approval records consent for one creation. After the approvals, resume with the returned `next` arguments, including `--operation <operation-id>` and the original `--root`.
6. If the result is `needs-browser`, give the user the returned URL. After the user completes that step, resume with its returned `command`, including `--operation <operation-id>`. Keep the same `--root`, `--documents-root`, and `--url` values throughout the flow. An explicit `--url` also applies to login and account commands.
7. When the result is `published`, give the user its Andocs URL. The CLI opens the link after sync. For a timeout, run the returned status `command` with `bunx andocs@latest` in place of `andocs`. It uses `publish status --operation <operation-id> --url <server-origin> --json`. For a branch conflict, resume with `--operation <operation-id> --new-operation` to plan the current files for the linked project.

Publish uploads the documentation root, `.andocs/`, and allowlisted files from `.agents/` and `.claude/` to GitHub, then syncs them to Andocs. New repositories are private. Existing linked repositories use their configured documentation path. An existing project can also receive a new private repository. Choose a contained documentation folder such as `docs/`. Publication is free. The Andocs link requires project membership.

Local prototype datasets stay on this computer. They do not move with publication. Refused files appear in `omitted` with their reasons.

Without `--json`, `publish --dry-run` shows a plain-text plan with the requested target flags, upload size, and omitted files. With `--operation`, it states that the stored target and approvals were not checked. Otherwise, it lists the creation approvals implied by the flags. It shows up to 10 selected files and 10 omitted files, then reports how many remain. With `--json`, the result keeps the full file lists and omission reasons. A dry run does not create or upload resources.
